# Phase output contract

Every phase output is a durable handoff. The next agent must be able to continue from this file and the listed inputs without replaying the current chat.

## Front matter

Every artifact begins with YAML-like front matter:

```yaml
---
schema_version: "0.2"
task_id: "task-id"
phase: "phase-name"
status: "ready"
agent: "agent-name"
inputs:
  - "relative/path/to/input"
assumptions:
  - "explicit assumption"
---
```

Use the actual task ID and phase. Keep input paths relative to the task directory where possible. If there are no assumptions, write `assumptions: []`; do not leave the field ambiguous.

Artifact schema `0.2` is current; `0.1` remains readable for existing sessions. Route-sensitive phases may add `risk_level`, `route_add`, and `route_reason`. The orchestrator accepts only safe additive changes and records each accepted change in `route.json`.

## Required body sections

Every report must contain, in an order appropriate to its template:

1. **Decision or work performed** — what this phase actually did.
2. **Scope** — what was included and excluded.
3. **Evidence** — commands, paths, tests, diffs, observations, or approvals.
4. **Assumptions and deviations** — anything not directly established by evidence.
5. **Failures and limitations** — including unavailable tools, baseline failures, skipped checks, and stale inputs.
6. **Risks** — what could still be wrong or unsafe.
7. **Next action** — the exact next phase, human decision, or blocker resolution.

## Status values

- `ready`: output is complete enough for the next phase.
- `needs-review`: a human decision, ambiguity, approval, or accepted risk is required.
- `blocked`: safe or honest progress is impossible with current inputs or environment.
- `verified`: only `verification.md` may use this for a fully evidenced final decision.

Do not use `done`, `complete`, `passed`, or `looks-good` as substitutes for the controlled vocabulary.

## Evidence rules

- Cite the exact command, path, test case, diff, or decision that supports a claim.
- Record command exit codes and relevant output summaries.
- Distinguish observed facts from model reasoning and inferences.
- Say “not run,” “not available,” or “not proven” instead of filling a gap with confidence.
- Preserve earlier failure reports; append a new fix or verification report rather than rewriting history.

## Content rules

- Use concise Markdown, tables, and checklists.
- Do not include hidden chain-of-thought, credentials, tokens, cookies, private keys, or unnecessary personal data.
- Do not paste the entire repository or conversation into an artifact.
- Link findings to requirement IDs, task IDs, file paths, and evidence.
- If the artifact is generated by a model, the orchestrator must still validate its presence and required fields.

## Handoff quality checklist

- [ ] Another agent can identify what to do next.
- [ ] All required inputs are named and actually available.
- [ ] Claims have evidence or are explicitly marked uncertain.
- [ ] Status matches the evidence.
- [ ] Scope drift and unrelated findings are recorded separately.
- [ ] Sensitive information is absent or redacted.
